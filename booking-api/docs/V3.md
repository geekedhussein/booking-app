# V3 — Service providers

V3 turns Reserve from one venue's booking system into a place where many
**service providers** each run their own calendars, and **clients** find them
and book. This document follows the V2 format: the idea first, then how it is
built here, then the contract.

---

## 1. The model

| Concept | Who | In the database |
| --- | --- | --- |
| Client | Books time | `users.role = 'customer'` |
| Service provider | Is booked | `users.role = 'provider'` + one `providers` document |
| Provider page | Where clients book them | `providers.slug` → `/p/<slug>` |
| Calendar | One thing that can be booked: the provider themselves, a room, a court | `resources` document with `provider_id` |
| Platform operator | Runs the whole site | `users.role` is `'staff'` or `'admin'` |

A provider can own several calendars (a tennis club with two courts) or just
one (a physiotherapist). With one calendar, the frontend skips the choice and
shows the booking view directly on the provider's page.

Calendars created before V3 have `provider_id: null`. They keep working as
"house" calendars run by staff; they don't appear in the directory.

---

## 2. Theory: authorization by ownership

Until V2, authorization was **role-based** (RBAC): "staff may edit resources".
That breaks as soon as there are many providers. Every provider has the same
role, but provider A must not edit provider B's calendar. The question changes
from *what are you?* to *is this yours?*

That second question can only be answered with **the record in hand**, so it
cannot live in route middleware. It belongs in the service, after the record is
loaded:

1. **Route:** `authorize('staff','admin','provider')`. Clients are out.
2. **Service:** load the calendar. If it doesn't exist, return **404**.
3. **Service:** `assertCanManageResource(user, row)`. Staff pass; a provider
   passes only if `row.owner_user_id === user.id`. Anyone else gets **403**.

Skipping step 3 creates the most common real-world API vulnerability, an
**IDOR** (insecure direct object reference). The route is protected, the id is
guessable, and anyone with the right role can change anyone's data by changing
a number in the URL. The e2e tests try exactly that with a second provider.

Ownership comes from the database record and the token, never from the request
body. A request that says `"providerId": 7` proves nothing.

Bookings follow the same rule, one step removed: a booking belongs to a
calendar, which belongs to a provider. `canManageBooking` loads the calendar
and asks the same question. The client who made a booking keeps their own
rights (cancel, reschedule, history) through the existing `isOwner` check.

All of it lives in one small module, `src/utils/access.js`, so the rule is
written once and every service asks it the same way.

## 3. Theory: sign-up that creates two things

A provider account is two documents: the user and their page. If the user were
written and the page insert failed (say the address is taken), we would have
a provider with no page, a state the rest of the app never expects.

Both inserts run **in one multi-document transaction** (MongoDB needs a replica
set for these; see `docs/MONGODB.md`), so either both exist or neither does. The e2e test checks the "neither" case: after a failed sign-up with a
taken address, the same email can still register.

**Signup can never create staff or admin.** `accountType` accepts only
`client` and `provider`; the zod schema rejects anything else with a 400.
Raising someone's privileges stays a deliberate, out-of-band act.

---

## 4. Theory: human-readable addresses (slugs)

`/p/dr-amelie-lee` is easier to share than `/p/42`. A slug has to be:

- **valid:** lowercase letters, digits and single hyphens, 3–40 characters.
  The zod schema checks it, and the collection's `$jsonSchema` validator
  guarantees it.
- **unique:** a unique index on `slug` (slugs are always lowercase, which the
  validator enforces, so case can't sneak in a duplicate). The index is
  what makes uniqueness true under concurrency. "Check whether it's free,
  then insert" alone would race, exactly like the naive booking check.
- **forgiving when derived:** if the person doesn't choose an address, we
  derive one from their name (`slugify`: strip accents, lowercase, hyphenate)
  and take the first free one: `dr-amelie-lee`, then `dr-amelie-lee-2`, and so
  on. A derived address never fails sign-up.
- **strict when chosen:** a chosen address that's taken is a field error
  (`details: [{ field: 'slug' }]`), so the form can show it under the input.

Changing an address later is allowed, and it breaks links already shared.
The dashboard warns about this before saving. Keeping old addresses as
redirects is a possible later improvement.

---

## 5. Theory: the directory query

The directory lists providers with **at least one active calendar**: an
empty page helps nobody. It's a single aggregation pipeline
(`listDirectory` in `provider.repository.js`): a `$lookup` that counts each
provider's active calendars, then a `$match` that drops providers with none, so
the count comes back with the page at no extra cost.

Search is a case-insensitive regular expression on the name and headline. The
user's text is escaped first (`.`, `*`, `(` and the rest), so it's matched
literally rather than as a pattern; unescaped, a crafted pattern could also be
made very slow (ReDoS). At directory scale a scan is fine; with many thousands
of providers you would add a text index or Atlas Search.

## 6. What changed, file by file

**New**
- `db/migrations/002_providers_and_calendars.js`: the `providers` collection
  (validator, unique `slug` and `user_id`), `resources.provider_id`. (Since the
  MongoDB switch the migrations are grouped by area rather than by version.)
- `utils/access.js`: `isStaff`, `ownsResource`, `canManageResource`,
  `assertCanManageResource`.
- `repositories/provider.repository.js`, `services/provider.service.js`,
  `schemas/provider.schemas.js`, `controllers/provider.controller.js`,
  `routes/provider.routes.js`: the provider feature, layered like every
  other.

**Changed**
- `auth.schemas` / `auth.service`: `accountType`, `displayName`, `headline`,
  `slug` on register; the user DTO carries `provider` (null for others) on
  register, login, refresh and `/auth/me`.
- `resource.repository`: every read looks up the owner (`$lookup`) (`owner_user_id`,
  `provider_slug`, `provider_name`); `insertResource` takes `providerId`;
  `listResources` filters by `providerId`.
- `resource.service`, `availability.service`, `booking.service`: ownership
  checks on every write and on the day list, transitions, history and
  reschedule.
- `booking.repository`: a client's booking list looks up the calendar and
  provider names, so the frontend no longer has to fetch every resource to
  label bookings.
- `docs/openapi.js`: version 3.0.0, the provider paths and register fields.

## 7. API

```
POST   /v1/auth/register     { email, password, accountType?: 'client'|'provider',
                               displayName?, headline?, slug? }

GET    /v1/providers?q=&limit=     public directory
GET    /v1/providers/:slug         public page: profile + active calendars
GET    /v1/providers/me            my profile + all my calendars (incl. paused)
PATCH  /v1/providers/me            { displayName?, headline?, slug? }
GET    /v1/providers/me/bookings   ?from=YYYY-MM-DD&to=YYYY-MM-DD&status=
                                   default: today to today + 30 days, soonest first
```

Authorization changes on existing routes:

| Route | Before | Now |
| --- | --- | --- |
| `POST /resources` | staff | staff, or a provider (calendar becomes theirs) |
| `PATCH`/`DELETE /resources/:id`, `PUT …/availability` | staff | staff, or the owning provider |
| `GET /resources/:id/bookings` | staff | staff, or the owning provider |
| `POST /bookings/:id/confirm` · `/complete` · `/no-show` | staff | staff, or the owning provider |
| `DELETE /bookings/:id`, `PATCH /bookings/:id`, `GET …/audit` | client or staff | client, owning provider, or staff |

## 8. Tests

`tests/e2e/api.test.js` adds three end-to-end tests:

1. Provider sign-up creates a page; an identical name gets `-2`; a taken
   chosen address is a 400 on `slug` and rolls back; signup can't request
   `staff`; clients get `provider: null`.
2. Ownership: a second provider gets 403 editing, setting hours, completing,
   cancelling and reading the dashboard of the first; the client's list names
   the provider; the owner's dashboard shows the client's email.
3. The directory only lists providers with an active calendar; the public
   page hides paused calendars while `/providers/me` shows them.

The frontend's browser run (44 checks) covers the same flows through the UI,
on desktop and phone.

## 9. Frontend summary

- **Sign up** asks *I want to book* or *I offer services*. Providers add a
  name, an optional line about what they offer, and a page address
  suggested from the name.
- **Home** is the directory, with search.
- **`/p/:slug`** is the provider's page. With one calendar it is also the
  booking page.
- **Dashboard** (providers): the link to share, and every booking across their
  calendars, grouped by day, updating live, with the actions each status
  allows. *Mark completed* and *Mark no-show* appear once a booking has
  started.
- **Schedule** and **Calendars** are scoped to the provider's own calendars
  (staff still see everything, with a Provider column).
