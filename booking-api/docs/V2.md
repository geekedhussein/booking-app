# V2 — Improvements & New Features

This document accumulates the V2 work: what each milestone adds, the reasoning,
and how to use/verify it. V1 (the original build) is documented in the root
`README.md` and `CLAUDE.md`.

---

## V2.1 — Hardening baseline

Five edge-layer defenses, added early in the middleware chain so bad or dangerous
traffic is rejected before it reaches business logic.

### CORS (`cors`)
Browsers block cross-origin reads unless the API opts in (Part II). We allow only
an **allowlist** of origins from `CORS_ORIGINS` (never `*` with credentials).
Non-browser callers (curl, mobile, server-to-server) send no `Origin` and are
unaffected — CORS is browser-enforced.

### Security headers (`helmet`)
Sets defensive response headers: `Strict-Transport-Security`, `X-Content-Type-Options:
nosniff`, `X-Frame-Options`, a baseline `Content-Security-Policy`, etc. Secure
defaults (Part IX).

### Request timeout (`src/middleware/request-timeout.js`)
Every request must finish within `REQUEST_TIMEOUT_MS` or gets a `503`. Prevents a
hung request from tying up a connection and eventually exhausting the pool.
(Ends the response; fully cancelling downstream work needs AbortSignal plumbing —
a later enhancement.)

### Rate limiting (`src/middleware/rate-limit.js`)
Redis-backed (so the limit is correct across instances — an in-memory limit would
multiply by instance count). A lenient **global** limiter (`RATE_LIMIT_MAX`/window)
and a strict **auth** limiter (`AUTH_RATE_LIMIT_MAX`) on `/auth/*` for brute-force
defense. Disabled under `NODE_ENV=test` to avoid flaky, order-dependent suites.

### Future-date booking validation (`src/schemas/booking.schemas.js`)
Semantic validation (Part IV): `startsAt` must be in the future and within
`BOOKING_MAX_ADVANCE_DAYS`. Closes the "book a slot in the past" gap.

### New config
`CORS_ORIGINS`, `REQUEST_TIMEOUT_MS`, `RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_MAX`,
`AUTH_RATE_LIMIT_MAX`, `BOOKING_MAX_ADVANCE_DAYS` (see `.env.example`).

### Verified
helmet headers present · allowed CORS origin echoed, disallowed one not ·
`RateLimit-*` headers present · future booking `201`, past `400`, too-far `400` ·
11th+ auth attempt in a window → `429`.

## V2.2 — Idempotency-Key on POST /bookings

Gives clients **exactly-once** semantics for booking creation, so a double-click,
a lost-response retry, or a mobile auto-retry never creates a duplicate.

### How it works
The client sends an optional `Idempotency-Key: <unique>` header. The server:
1. **Fingerprints** the request (method + path + sorted body → SHA-256).
2. **Atomically claims** the key via `INSERT ... ON CONFLICT DO NOTHING` on a
   `UNIQUE (user_id, idempotency_key)` index (same "let the DB serialize it"
   trick as the booking overlap constraint).
3. On a win: runs the request, captures the response, stores it (`completed`).
4. On a duplicate:
   - `completed` → **replays** the stored response (with header
     `Idempotent-Replay: true`), no re-execution.
   - `in_progress` → `409` "already being processed".
   - different fingerprint → `409` "used with different parameters".
5. If the original failed with a `5xx`, the claim is **released** so a retry can
   proceed (transient failures aren't cached).

### Files
- `src/db/migrations/005_idempotency.sql` — the `idempotency_keys` table.
- `src/repositories/idempotency.repository.js` — atomic `claimKey`, `completeKey`,
  `releaseKey`.
- `src/middleware/idempotency.js` — the middleware (on `POST /bookings`, after
  `authenticate`).

### Client guidance
Generate a fresh UUID per logical booking attempt and reuse it across retries of
that same attempt. Do NOT reuse a key for a different booking.

### Verified
First request `201` → replay returns the identical booking with
`Idempotent-Replay: true` → same key + different body `409` → 6 concurrent
same-key requests produced **exactly one** booking (mix of `201` originals/replays
and `409` in-progress). Expired-key cleanup is deferred to the V2.9 scheduler.

### Note
`idempotency_keys` grows over time; rows carry `expires_at` (24h). The periodic
cleanup job is added in V2.9 (scheduling). Until then, expired rows are harmless
but accumulate.

## V2.3 — Transactional outbox

Closes the dual-write gap: previously we committed the booking, THEN enqueued the
confirmation as a separate write to Redis. A crash in between lost the event
forever. There is no ordering of two independent systems that avoids this window.

### How it works
1. `createBooking`/`cancelBooking` run inside `withTransaction`. In that single
   transaction they insert the booking AND an `outbox` row describing the event.
   They commit together — atomic — so a booking can never exist without its event
   (and vice versa).
2. A separate **relay** process (`src/outbox-relay.js`, `npm run relay`) polls the
   outbox for due rows and delivers each to Redis: enqueue the confirmation
   (→ worker) and publish the real-time event (→ WebSocket subscribers). Then it
   marks the row `processed`.
3. Delivery is **at-least-once** (a crash after delivery but before marking =
   redelivery), which is safe because consumers are idempotent (BullMQ jobId
   dedup + the worker's guard).

### Reliability details
- **FOR UPDATE SKIP LOCKED** when claiming a batch → multiple relay instances can
  run concurrently without processing the same row twice.
- **Retry with backoff**; rows exceeding `OUTBOX_MAX_ATTEMPTS` become `failed`
  (a dead-letter you can inspect).
- Documented tradeoff: the relay delivers to Redis while holding the row lock
  inside the transaction — simple and correct for modest volume; a
  higher-throughput variant would claim, deliver outside the lock, then mark.

### Files
- `src/db/migrations/006_outbox.sql` — the `outbox` table.
- `src/repositories/outbox.repository.js` — `insertEvent` (transactional),
  `fetchDueBatch`, `markProcessed`, `markRetry`.
- `src/outbox-relay.js` — the relay process. Added to `docker-compose.yml`.
- `src/services/booking.service.js` — refactored to write booking + event in one
  transaction (no more direct enqueue/publish).
- `src/repositories/booking.repository.js` — `insertBooking`/`cancelBooking` now
  accept a transaction executor.

### New processes / config
Run three background-capable processes now: the API, the **worker** (email), and
the **relay** (outbox delivery). Config: `OUTBOX_POLL_INTERVAL_MS`,
`OUTBOX_BATCH_SIZE`, `OUTBOX_MAX_ATTEMPTS`.

### Verified
- **Atomicity**: forcing the outbox insert to fail rolled the booking back too
  (both-or-neither).
- **Durability**: a booking created while the relay was OFF committed with a
  pending outbox row and delivered NOTHING to Redis; starting the relay then
  delivered the event and the confirmation was sent — the event that V1 would
  have lost.

### Trade-off vs V1
Real-time/email delivery now has a small latency (up to one poll interval) since
it goes through the outbox instead of firing inline. That's the price of never
losing an event — a good trade for anything that matters.

## V2.4 — Auth hardening

Turns auth from "works" into "resists real attackers": short access tokens with
revocable refresh tokens, rotation with theft detection, and per-account lockout.

### Access + refresh tokens
- **Access token**: short-lived JWT (`JWT_EXPIRES_IN`, now `15m`), verified
  statelessly on every request. Small blast radius if stolen.
- **Refresh token**: long-lived opaque random string, stored **hashed** server-side
  (`refresh_tokens` table). Used only at `POST /auth/refresh`. Because it has a
  server record, it CAN be revoked — the capability plain JWTs lacked (Part IV).

`register`/`login` now return `{ user, accessToken, refreshToken }`.

### Rotation + reuse detection
Every refresh **rotates**: the old token is marked used and a new one issued in
the same `family_id`. Presenting an already-used token = theft signal → the whole
family is revoked (`Refresh token reuse detected`). Verified: rotation issues a
different token; reusing the old one 401s and kills the new one too.

### Logout / revocation
- `POST /auth/logout {refreshToken}` → revoke that token (`204`).
- `POST /auth/logout-all` (access token) → revoke all of the user's tokens.
Verified: refresh after logout → `401`; refresh after logout-all → `401`.

### Account lockout
`recordFailedLogin` increments a per-user counter and sets `locked_until` after
`MAX_FAILED_LOGINS` (5); a successful login clears it. Verified: 6 wrong logins →
6th is `FORBIDDEN`, and a correct password while locked is still `FORBIDDEN`.

Rate limiting (V2.1, per-IP) and lockout (per-account) are complementary layers.
In single-IP testing the IP limiter trips first — expected; they defend different
attack shapes (one abusive IP vs. one targeted account from many IPs).

### Files
`007_auth_hardening.sql` · `repositories/refresh-token.repository.js` ·
`utils/token.js` · reworked `services/auth.service.js`, `controllers/auth.controller.js`,
`routes/auth.routes.js`, `schemas/auth.schemas.js`, and lockout helpers in
`repositories/user.repository.js`.

### Config
`JWT_EXPIRES_IN` (now `15m`), `REFRESH_TOKEN_EXPIRES_DAYS`, `MAX_FAILED_LOGINS`,
`LOCKOUT_DURATION_MINUTES`.

### Client guidance
Store the refresh token securely (httpOnly cookie for browsers is safer than
localStorage). On a `401` from an access-token request, call `/auth/refresh` once
and retry; if that also fails, send the user to log in again.

### Enumeration note
The lockout response reveals an account exists — a deliberate, standard tradeoff
(silently failing confuses legitimately locked-out users). Login itself still
returns one generic message for wrong-password vs. no-such-user.

## V2.5 — Account flows: email verification & password reset

Adds the two account flows every real app needs, both via single-use, hashed,
expiring tokens delivered through the existing outbox → relay → queue → worker
email pipeline.

### Generalized notification pipeline
`src/queue/booking-queue.js` → `src/queue/notifications.js`: one queue for all
outbound email, with `enqueueNotification({ type, payload, dedupeId })`. The
worker dispatches by `type` (`booking.confirmation`, `email.verification`,
`password.reset`). The relay dedupes by outbox row id, so at-least-once delivery
never double-sends.

### Email verification
Registration inserts the user, a hashed verification token, AND the outbox email
event — all in ONE transaction (V2.3). `POST /auth/verify-email {token}` redeems
it (single-use) and sets `email_verified`. `/auth/me` now returns `emailVerified`.
`POST /auth/resend-verification {email}` issues a fresh one (generic response).

### Password reset
`POST /auth/forgot-password {email}` → always `200` generic (no account
enumeration); only a real account gets a reset event. `POST /auth/reset-password
{token, password}` verifies the token, updates the password, and — importantly —
**revokes all refresh tokens** (a reset implies compromise) and clears lockout.

### Security properties (all verified)
- Verification token is single-use (reuse → `400`).
- Forgot-password is enumeration-safe (existing and unknown emails both `200`;
  only the real user gets an outbox event).
- After reset: old password `401`, new password `200`, old refresh token `401`.

### Files
`008_account_flows.sql` (adds `users.email_verified` + `auth_tokens`) ·
`repositories/auth-token.repository.js` · `queue/notifications.js` (was
`booking-queue.js`) · reworked `worker.js`, `outbox-relay.js`,
`services/auth.service.js`, `controllers/auth.controller.js`,
`routes/auth.routes.js`, `schemas/auth.schemas.js`; `markEmailVerified` /
`updatePassword` in `user.repository.js`.

### New endpoints
`POST /auth/verify-email` · `POST /auth/resend-verification` ·
`POST /auth/forgot-password` · `POST /auth/reset-password`

### Config
`APP_BASE_URL`, `EMAIL_VERIFICATION_EXPIRES_HOURS`, `PASSWORD_RESET_EXPIRES_MINUTES`.

## V2.6 — Availability windows & booking rules

Turns "reserve any time" into a real scheduling system with per-resource rules.

### Booking policies (per resource)
Columns on `resources`: `min_duration_minutes`, `max_duration_minutes`,
`lead_time_minutes`, `buffer_minutes` (all optional, safe defaults preserve old
behavior). Settable on create/update.

### Availability windows
`availability_windows` (resource_id, day_of_week 0–6, opens_at, closes_at) — one
resource can have several windows per day (split hours). No windows = always
available. Managed via:
- `GET /resources/:id/availability` (public)
- `PUT /resources/:id/availability` (staff/admin, full replacement)

### Where validation lives
Duration/lead-time/hours are **semantic** rules that need the resource's own data,
so they're validated in the **service layer** (`utils/booking-rules.js`, a pure
testable function), not in the static request schema. Principle: schema validates
what's knowable from the request; the service validates rules requiring domain
state.

### Buffer — enforced by the database, race-free
The buffer (gap between consecutive bookings) is NOT an application check (that
would be the check-then-insert race we avoid everywhere). Instead each booking's
`buffer_minutes` is denormalized onto the row, and the exclusion constraint was
recreated to pad each range on the END:
`tsrange(starts_at, ends_at + make_interval(mins => buffer_minutes), '[)')`.
"No overlap of padded ranges" == "at least `buffer` gap between real ranges."

### Files
`009_availability_and_rules.sql` · `utils/booking-rules.js` ·
`repositories/availability.repository.js` · `services/availability.service.js` ·
policy fields threaded through `resource.repository/service/schemas/controller/routes`
and `booking.repository` (`bufferMinutes`) / `booking.service` (rule check).

### Verified
Policies persist and return in the DTO · availability set/read · too-short `400`,
too-long `400`, outside-hours `400`, within-rules `201` · buffer: 0-min gap `409`,
15-min gap `201` (integration test locks this in).

## V2.7 — Capacity > 1

Resources can now allow N concurrent bookings (a class with seats, a shared desk
pool, a tour), not just exclusive single-slot use.

### Why the exclusion constraint had to go
An exclusion constraint is PAIRWISE ("no two overlap") and cannot express the
AGGREGATE rule "at most N overlap". So migration 010 drops `bookings_no_overlap`
and replaces it with a plain GiST index (speeds the count; no longer forbids
overlaps). The `ends_at > starts_at` CHECK stays.

### How capacity is enforced (race-safe, without a constraint)
In `createBooking`, inside one transaction:
1. `SELECT ... FROM resources WHERE id = $1 FOR UPDATE` — locks the resource row,
   SERIALIZING all bookings for that resource (different resources don't contend).
2. Count confirmed bookings whose buffered range overlaps the requested range.
3. If `count >= capacity` → `409`; else insert.

Because bookings for a resource are serialized on the lock, the count can't be
raced by a phantom insert (the failure mode of naive check-then-insert). This is
the standard pattern for capacity/quota enforcement, which a declarative
constraint can't do.

capacity = 1 is just the special case "at most 1 overlapping" = the old
no-overlap behavior. Buffer still works (the count compares buffered ranges).

### Trade-off (documented honestly)
The overbooking guarantee now lives in the service's locked transaction, not a DB
constraint — so a direct INSERT that bypasses the service could overbook. That's
inherent to "count <= N": it isn't expressible as a simple constraint. All writes
must go through the service.

### Files
`010_capacity.sql` · `booking.repository.js` (`lockResourceForBooking`,
`countOverlappingConfirmed`) · `booking.service.js` (lock → count → check →
insert). Integration tests rewritten to exercise the service.

### Verified
capacity 1 overlap `409` · capacity 3 → 3 `201` then `409` · **6 concurrent
requests on a capacity-2 slot → exactly 2 confirmed** (the race-safety proof) ·
buffer still enforced.

## V2.8 — Reschedule, state machine & audit trail

Adds lifecycle and accountability to bookings.

### State machine (`utils/booking-state.js`)
States: `pending → confirmed → completed | no_show | cancelled`. Legal transitions
are a data table; illegal moves are rejected (`400`) by construction, preventing
impossible states. Only `pending`/`confirmed` occupy capacity (ACTIVE_STATES);
terminal states free the slot. Migration 011 widens the status CHECK and the
capacity index predicate to the active states.

### Reschedule (`PATCH /bookings/:id`)
Moving a booking re-runs the full creation checks — resource rules AND the
capacity count under the resource lock (V2.7), **excluding the booking being
moved** from its own count — atomically. Only allowed from an active state.
Owner or staff.

### Transitions
- `DELETE /bookings/:id` → cancel (owner or staff)
- `POST /bookings/:id/confirm` · `/complete` · `/no-show` (staff only)
All go through one generic `transitionBooking` that authorizes, checks the
transition is legal, updates status with an optimistic guard (`WHERE status =
fromStatus`, so concurrent changes are caught), and writes an audit row.

### Audit trail (`booking_audit` + `GET /bookings/:id/audit`)
Every change (created/rescheduled/cancelled/completed/no_show/confirmed) writes an
append-only row — actor, action, from→to status, before/after details — in the
SAME transaction as the change. Distinct from the outbox (delivery): this is
durable history for accountability. Readable by owner or staff.

### Files
`011_state_and_audit.sql` · `utils/booking-state.js` ·
`repositories/booking-audit.repository.js` · `booking.repository.js`
(`countOverlappingActive` with exclude, `updateStatus`, `reschedule`) ·
rewritten `booking.service.js`, `booking.controller.js`, `booking.routes.js` ·
`rescheduleBookingBody` schema · relay handles `booking.rescheduled`.

### Verified
Reschedule (owner) moves times & frees old slot · customer→complete `403`,
staff→complete `200` · cancel/reschedule of a completed booking `400` (state
machine) · audit trail shows `created → rescheduled → completed`. Integration
tests lock in reschedule, the illegal transition, and the audit lifecycle.

## V2.9 — Scheduled reminders & cleanup jobs

Adds **time-triggered** work (Part VII's scheduling half) alongside the existing
event-triggered jobs. New process: `npm run scheduler` (`src/scheduler.js`), also
added to `docker-compose.yml`.

### Reminders
Every tick, claim bookings starting within `REMINDER_LEAD_HOURS` that haven't been
reminded, and record a `booking.reminder` outbox event for each. The relay then
enqueues it and the worker "sends" the email.

**Exactly-once** is the hard part — a booking sits inside the reminder window for
many ticks. Solved by a persistent marker claimed atomically:
`UPDATE bookings SET reminder_sent_at = now() WHERE ... reminder_sent_at IS NULL
... RETURNING` (with `FOR UPDATE SKIP LOCKED`). Claiming and marking are the same
statement, so there's no window for a double-send, and multiple scheduler
instances can't both claim the same row. The claim and the outbox intent commit in
ONE transaction (V2.3), so a crash can't lose the reminder either.

### Multi-instance safety
Two independent defenses, because duplicate emails are user-visible:
1. **Redis distributed lock** (`SET key NX PX ttl`) so only one instance runs a
   job per tick; the TTL means a crashed holder's lock expires. Released with a
   compare-and-delete Lua script so you never delete someone else's lock.
2. **Atomic DB claiming** (above) as the backstop.

### Retention cleanup
Runs every 60th tick: expired idempotency keys (deferred from V2.2), used/expired
auth + refresh tokens, and processed outbox rows older than `RETENTION_DAYS`
(deferred from V2.3). `failed` outbox rows are deliberately KEPT — that's the
dead-letter queue you inspect.

### Files
`012_reminders.sql` (adds `bookings.reminder_sent_at` + partial index) ·
`src/scheduler.js` · `repositories/cleanup.repository.js` ·
`claimBookingsDueForReminder` in `booking.repository.js` · relay + worker handle
`booking.reminder`.

### Config
`SCHEDULER_INTERVAL_MS`, `REMINDER_LEAD_HOURS`, `REMINDER_BATCH_SIZE`,
`RETENTION_DAYS`.

### Verified
Booking 12h out → reminded; booking 5 days out → not · a second tick queued ZERO
reminders (exactly-once held) · relay+worker delivered the reminder email ·
cleanup removed an expired idempotency key and a 30-day-old processed outbox row.

## V2.10 — API maturity

Four changes that make the API consumable by other teams.

### URI versioning (`/v1`)
All API routers now mount under `/v1` (`/v1/auth`, `/v1/resources`,
`/v1/bookings`, `/v1/webhooks`). A future breaking change ships as `/v2` while
`/v1` keeps working. `/health` stays UNVERSIONED — it's infrastructure that load
balancers poll, not part of the API contract. Unversioned API paths now 404.

### Cursor pagination (`GET /v1/bookings/me`)
Offset pagination makes the DB walk and discard rows (`OFFSET 10000`) and shifts
results under concurrent inserts. A cursor encodes the last row's
`(starts_at, id)`; the query becomes a keyset lookup
`WHERE (starts_at, id) < (cursorKey, cursorId)` — index-friendly and stable.
Cursors are opaque base64url blobs (pass back verbatim; don't parse them).
Request with `?cursor=…` or `?paginate=cursor`; the response carries
`pagination.nextCursor` (null on the last page). Offset paging is retained for
backward compatibility. Trade-off: forward-only, no random access to "page 47".

### OpenAPI (`/docs`, `/docs/openapi.json`)
A machine-readable contract (11 paths) that drives the browsable Swagger UI at
`/docs` and can generate client SDKs or power contract tests. Code-first —
update it in the same PR as any route change.

### Webhooks (`/v1/webhooks`)
Subscribers register a URL + event types and receive `POST`s instead of polling.
- **Signing**: HMAC-SHA256 over `${timestamp}.${rawBody}`, sent as
  `x-webhook-signature` + `x-webhook-timestamp`. The timestamp is inside the
  signed material so captured requests can't be replayed forever. Verification
  uses `timingSafeEqual` (Part IX).
- **Secret** returned ONCE at registration (like an API key), never on list.
- **Retries** with exponential backoff; 4xx (except 429) is treated as a
  permanent rejection and not retried. Every attempt is recorded in
  `webhook_deliveries` (inspect via `GET /v1/webhooks/:id/deliveries`).
- **Delivery is driven by the outbox relay** (V2.3), so events can't be lost, and
  a broken subscriber never blocks the pipeline.

### Files
`013_webhooks.sql` · `utils/cursor.js` · `utils/webhook-signing.js` ·
`repositories/webhook.repository.js` · `services/webhook.service.js` ·
`webhook.{controller,routes,schemas}.js` · `docs/openapi.js` +
`routes/docs.routes.js` · `/v1` mounting in `app.js` · cursor support threaded
through booking repo/service/controller · relay dispatches webhooks.

### Verified
`/v1/resources` 200 and unversioned `/resources` 404 · `/docs` + `/docs/openapi.json`
200 (11 paths) · cursor paging walked 5 bookings 2-at-a-time with working
`nextCursor` · webhook delivered to a real receiver that **independently verified
the HMAC** (`signatureValid=true`), recorded `delivered/200/1 attempt`; a payload
signed with a different subscription's secret was correctly **rejected**
(`signatureValid=false` → 401) · secret hidden on list.

## V2.11 — Observability

Completes Part VIII's three pillars (logs were built in V1) and adds the health
checks production orchestrators actually need.

### Liveness vs readiness — two different questions
- `GET /health/live` (and `/health` alias) — "is the process alive?"
  **Dependency-free.** Failing it means the orchestrator RESTARTS the container,
  so it must never check the DB: a slow database would make every instance look
  dead and cause a fleet-wide restart storm.
- `GET /health/ready` — "can this instance SERVE traffic?" Checks Postgres (with
  a 2s timeout) and Redis. Failing it means the load balancer stops ROUTING here
  without killing the process, so it can recover on its own. The database is
  required; Redis is reported but doesn't fail readiness, because the cache
  degrades gracefully (V2.1).

Verified by actually stopping Postgres: `/health/live` stayed **200** while
`/health/ready` returned **503** with `database: error: ECONNREFUSED`, then
recovered to 200 once Postgres restarted. The Dockerfile healthcheck now targets
`/health/live`.

### Metrics (`GET /health/metrics`, Prometheus format)
Default process metrics (CPU, memory, **event-loop lag** — the direct signal that
something is blocking Node's single thread), HTTP request counter + latency
histogram, DB query latency, and domain counters (`bookings_created_total`,
`booking_conflicts_total`, `outbox_pending_events`).

**The cardinality rule**: metrics are labelled by ROUTE PATTERN
(`/v1/bookings/:id`), never the raw path — one series per booking id would melt
the metrics backend. Unmatched requests bucket to `unmatched` so URL scanners
can't explode the label space.

A real wrinkle handled here: Express resets `req.baseUrl` to `''` while unwinding
to the error handler, so error responses would be mislabelled `/:id` instead of
`/v1/bookings/:id`. Fixed with `captureMountPath`, mounted first on each router.

### Tracing (`observability/tracing.js`)
`AsyncLocalStorage` propagates a trace context through async calls without
threading a `ctx` parameter everywhere. `withSpan()` times nested operations —
every DB query is a span carrying the first 60 chars of SQL (never parameters).
Traces are **sampled by latency**: only requests over 250ms or with a 5xx emit
the span breakdown, because tracing everything is expensive and noisy. Swapping
in OpenTelemetry means replacing this module's internals; callers don't change.

### Error tracking (`observability/error-tracker.js`)
Unexpected (5xx) errors are captured with request id, route, method and user, and
**fingerprinted** (error type + first stack frame) so 10,000 occurrences of one
bug group into one issue. Operational 4xx errors are deliberately NOT captured —
they're normal traffic. A thin seam: swap the body for a Sentry SDK call and all
call sites keep working.

### Files
`observability/{metrics,tracing,error-tracker}.js` · `middleware/metrics.js` ·
rewritten `routes/health.routes.js` · instrumentation in `app.js`,
`db/index.js`, `middleware/error-handler.js`, `services/booking.service.js`,
`captureMountPath` on each router.

### Verified
readiness reflects real DB failure and recovery · metrics expose 72 process
series + domain counters (`bookings_created_total 4`, `booking_conflicts_total 1`)
· route labels are patterns, correct even on 404/409 error paths · traces emitted
for slow/error requests.

## V2.12 — Tooling: linting, CI/CD & load testing

The machinery around the code — what catches mistakes before production.

### ESLint + Prettier
Separate jobs, deliberately: **Prettier** owns formatting (ends style debates),
**ESLint** owns bug-finding. `eslint-config-prettier` (last in the flat config)
disables every stylistic ESLint rule so they never fight.

Rules chosen for value, not volume: `require-atomic-updates` and
`no-async-promise-executor` (async bugs are the nasty silent class in Node),
`no-unused-vars` with `^_` escape for Express's mandatory 4-arg error signature,
`eqeqeq`, `prefer-const`, `no-console` (use the logger).

**It immediately found a real bug**: duplicate `REDIS_URL` and `CACHE_TTL_SECONDS`
keys in the config schema — a silent shadowing introduced during V2. Fixed.
Scripts: `npm run lint`, `lint:fix`, `format`, `format:check`.

### CI (`.github/workflows/ci.yml`)
Runs on every push/PR: install (`npm ci` — lockfile-exact, reproducible) → lint →
format check → migrate → unit → integration → e2e, plus a separate job that builds
the Docker image (a broken Dockerfile should fail CI, not deploy day).

The key decision: **real Postgres and Redis service containers**, with health-check
gating so migrations can't race container startup. Running only unit tests in CI
would skip exactly the tiers that catch constraint and wiring bugs.

### Load testing (`scripts/load-test.js`)
The only tier that tests behaviour under sustained pressure.

**Contention scenario** — the real proof of the V2.7 capacity guarantee:
> 50 concurrent requests for a capacity-3 slot → **exactly 3 × 201, 47 × 409**,
> and the DB independently confirms 3 confirmed bookings. **PASS.**

**Throughput scenario** — 300 reads at concurrency 20: **502 req/s**, p50 36ms,
p95 53ms, p99 57ms. Percentiles, not averages: averages hide the slow tail real
users feel.

Note the contended path's ~342ms p50 is expected and correct — those requests are
serializing on the resource lock by design. That latency IS the safety guarantee.

## V2.12 — Tooling: linting, CI/CD & load testing

The machinery that keeps quality from eroding as the codebase grows.

### ESLint + Prettier
Two different jobs, deliberately separate: the **linter** catches correctness
problems (unused vars, loose equality, promise misuse); the **formatter** settles
style so nobody debates it in review. `eslint-config-prettier` sits last and
disables rules that would fight the formatter, so a lint failure always means
something real.

Notable tuning: `require-await` is OFF — it fires on async functions that
legitimately return a promise without awaiting (test mocks, thin pass-throughs),
which is correct code. `no-promise-executor-return` stays ON and immediately
found 6 real instances of `new Promise(r => setTimeout(r, ms))` returning the
timer handle; fixed by centralising `sleep`/`timeoutAfter` in `utils/sleep.js`.

Run: `npm run lint`, `npm run format`. **Current state: 0 lint errors, Prettier
clean across src/tests/scripts.**

### CI pipeline (`.github/workflows/ci.yml`)
Three jobs on every push/PR:
1. **quality** — eslint + prettier check.
2. **test** — spins up REAL Postgres 16 and Redis 7 as service containers with
   health checks (the runner waits until they accept connections), applies
   migrations, then runs all three test tiers. This is why the testing pyramid
   matters: unit needs nothing, integration/e2e need real infrastructure, and CI
   must provide it.
3. **build** — Docker image build, gated on the first two passing.

### Load testing (`scripts/load-test.js`)
The only tier that can falsify "no overbooking under load". Fires N concurrent
bookings at one capacity-M slot and asserts EXACTLY M exist afterwards.

Results (local Postgres/Redis):

| Concurrency | Capacity | Created | Status codes | Throughput |
|---|---|---|---|---|
| 200 | 5 | **5** | 5×201, 195×409 | 144 req/s |
| 500 | 1 | **1** | 1×201, 499×409 | 162 req/s |
| 1000 | 20 | **20** | 20×201, 980×409 | 228 req/s |

No overbooking, no errors, no lock timeouts, no pool exhaustion at any scale —
the V2.7 resource-lock design holds under genuine sustained contention, not just
the 6-request demo.

Run: `npm run loadtest -- 500 10` (API must be running).

## Frontend support (added with the React app)

Two read endpoints the booking UI needs, plus two fixes found while building it.

- `GET /v1/resources/:id/schedule?date=YYYY-MM-DD` — **public**. The taken time
  intervals for one day, plus capacity, buffer and that day's opening windows.
  Exposes only intervals, never who booked them. Lets the UI show availability
  before a booking attempt; the server's locked capacity check stays
  authoritative.
- `GET /v1/resources/:id/bookings?date=YYYY-MM-DD` — **staff only**. Every
  booking on that day (any status) with the booker's email, for the staff
  schedule.
- **Fix:** `PATCH /v1/resources/:id` now accepts `maxDurationMinutes: null` to
  clear a limit.
- **Fix (V2.10 bug):** the strict query schema rejected `?paginate=cursor`, so
  the first page of cursor pagination always returned 400. The V2.10 test output
  showed this and it was missed. Fixed, with an e2e regression test.

Files: `booking.repository.js` (`listByResourceAndDay`), `booking.service.js`
(`getResourceSchedule`, `listResourceBookingsForDay`), `resource.schemas.js`
(`dayQuery`, nullable max duration), `booking.schemas.js` (`paginate`),
`resource.controller.js`, `resource.routes.js`, `booking.controller.js`,
`openapi.js`. `docker-compose.yml` gains a `web` service (`../booking-web`) and
